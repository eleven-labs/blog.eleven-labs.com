# Concepts and Architecture

## Concepts

This Design System is based on **four concepts**:

- **Design Tokens**

    > Design tokens are the visual design atoms of the design system — specifically, they are named entities that store visual design attributes. We use them in place of hard-coded values (such as hex values for color or pixel values for spacing) in order to maintain a scalable and consistent visual system for UI development. [Salesforce, Lightning Design System](https://www.lightningdesignsystem.com/design-tokens/).

    Our tokens are declared in CSS, inside the `@theme` block of `src/design-system/styles/theme.css`.
    **Tailwind CSS v4** turns each of them into a CSS custom property *and* into a family of utility
    classes, so a single declaration feeds both the stylesheet and the markup.

    See [Design Tokens / About](/docs/foundations-design-tokens-about--docs) for the details.

- **Atomic Design**

    [**Atomic Design**](https://atomicdesign.bradfrost.com/) is a modular design approach conceived by [**Brad Frost**](https://bradfrost.com/) to build Design Systems out of simpler components: atoms, molecules, organisms, templates and pages.

    ![Atomic Design](documentations/imgs/atomic-design-tokens.jpg)

- **Utility classes**

    Every style is written as a Tailwind utility class, directly in the markup. Components no longer
    ship a stylesheet of their own: what used to be a BEM block is now a list of classes, and what
    used to be a SCSS modifier is now a [**cva**](https://cva.style/) variant.

    ```tsx
    export const buttonVariants = cva('inline-flex items-center rounded-[100px] px-m py-xs', {
      variants: {
        variant: {
          primary: 'bg-info text-white',
          secondary: 'border-2 bg-white text-info hover:border-info',
        },
      },
    });
    ```

    Only three things still justify handwritten CSS, and they all live next to what they style:
    the markdown content (`PostContent.css`), the newsletter form rendered by Webmecanik
    (`webmecanik.css`), and the twelve colour/icon pairs of the `Reminder` (`Reminder.css`).

- **All components are polymorphic**

  A polymorphic component can adopt the behaviour and appearance of any HTML element. The same
  component renders as an anchor or as a button while staying visually identical.

  > We use the `react-polymorphed` library, for more details, you can read this [documentation](https://www.npmjs.com/package/react-polymorphed)

## Composing classes

Components merge their own classes with the ones they receive through `cn`, a thin wrapper around
[`clsx`](https://github.com/lukeed/clsx) and [`tailwind-merge`](https://github.com/dcastil/tailwind-merge):

```tsx
<div className={cn('bg-white p-m', className)} />
```

`tailwind-merge` resolves conflicts, so a caller passing `bg-primary` really does replace `bg-white`
instead of relying on the order of the generated CSS. Because our scales are custom, they are
declared a second time in `helpers/cn.ts`: anything added to `theme.css` must be added there too.

## Architecture

### Directory and file architecture in this project

```
└───src
│   └───design-system
│   │   └───assets
│   │   └───components
│   │   └───constants
│   │   └───documentations
│   │   └───helpers
│   │   └───hooks
│   │   └───styles
│   │   └───types
```

The design system lives in the `src/design-system` folder of the blog. It only holds generic
components: everything tied to the blog itself (cards, blocks, header, footer, templates and pages)
lives beside it, in `src/components`, `src/templates` and `src/pages`.

#### assets:

The assets of the Design System: the logo and the icons, as SVG files. `pnpm build:design-system`
optimises them with **svgo** and turns them into React components with **svgr**.

#### components:

```
└───src
│   └───design-system
│   │   └───components
│   │   │   └───Atoms
│   │   │   └───Molecules
```

This folder only contains UI components. Each of them must have an associated story.
These components must not have any business logic, nor state management (they can only be manipulated thanks to their properties).

What is essential to a component:

- Define the **properties interface**, extending the native element's props when it renders one
- Accept a `className` and merge it with `cn`, so the caller can adjust spacing or colour
- Express its variants with **cva** rather than with a boolean-driven class name
- Have an associated **story** to be able to view it in **storybook**

#### constants:

Names of the design tokens, in their reading order, and the helper that reads their values back from
the stylesheet for the documentation.

#### documentations:

Here is all the documentation that will be used by the storybook.

#### helpers:

Helper functions make complicated or repetitive tasks a bit easier, and keep your code DRY. `cn` and
`polyRef` both live here.

#### styles:

```
└───src
│   └───design-system
│   │   └───styles
│   │   │   └───index.css      ← entry point
│   │   │   └───theme.css      ← the design tokens
│   │   │   └───base.css       ← global rules completing Tailwind's preflight
│   │   │   └───utilities.css  ← the utilities Tailwind does not provide
```

`index.css` imports Tailwind, then the three files above. The application entry point,
`src/styles.css`, imports it and adds the two stylesheets that belong to the blog rather than to the
design system.

#### types:

These are all common types related to the whole design system, **component property interfaces** should not be included.
